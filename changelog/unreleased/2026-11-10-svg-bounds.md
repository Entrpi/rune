- **An SVG draws only `data:` images unless its cache trusts it, and its decode is bounded for the resources Rune owns:** an `<image href>` naming a local file reads nothing by default, so an SVG from a web response or a model's reply can't embed the user's files or hang a decode thread on a FIFO or `/dev/zero`; `ImageCache::svg_file_images(true)` lets an app's own SVGs read regular files again. SVGZ inflates to at most 64 MiB; a document nesting past 64 elements is refused before the XML parses (a thousand nested `<svg>` used to overflow a decode thread's stack and abort the app); after usvg builds the tree its nodes are counted (a `<use>` fan-out past 100,000 is refused) and the pixels its images and pattern tiles would draw are counted in saturating `f64` (a 20,000 px tile, or a raster near `u32::MAX` a side, is refused); and every SVG raster is at most 4096 pixels a side, `url_set`'s listed widths included. Each refusal is an `Image::error`. Rune does not stop a reference cycle or loop among clip paths, masks, filters, gradients, patterns or markers, nor a mask/marker/`tref`/selector fan-out: usvg 0.45 resolves these before Rune's bounds run and, catching only one- and two-element cycles, overflows the stack on a longer ring or hangs on a gradient loop. These are usvg bugs, fixed upstream for the cycle and overflow class by linebender/resvg#1225 (an iterative cycle search) and #1223 (a configurable parse depth); Rune gets the fix by upgrading to the first resvg release that carries them.
